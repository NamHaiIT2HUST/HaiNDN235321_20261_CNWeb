Sơ đồ Component (Component Tree)

Ứng dụng được thiết kế theo tư tưởng phân rã thành các Functional Component độc lập, mỗi component đảm nhận một trách nhiệm duy nhất (Single Responsibility Principle):

<App /> (Root Component)
Quản lý State tập trung toàn cục
State: [kw, setKeyword], [newUser, setNewUser]
<SearchForm />
Ô tìm kiếm người dùng
Nhận: onChangeValue
<AddUser />
Form thêm người dùng mới
Nhận: onAdd
Local State: adding, user
<ResultTable />
Bảng hiển thị, lọc, sửa, xóa
Nhận: keyword, user, onAdded
Local State: users, loading, editing
User Rows
Render users.map()
Edit Modal
Sửa & Deep copy address
Vai trò chi tiết của từng Component trong cây:
  • App (Root Component): Nắm giữ vị trí cao nhất trong phân cấp, đóng vai trò "nhạc trưởng". App quản lý toàn bộ các state cần chia sẻ giữa các nhánh con (kw và newUser), sau đó phân phối chúng thông qua Props.
  • SearchForm: Chịu trách nhiệm render thanh tìm kiếm, nhận input gõ phím từ người dùng và kích hoạt sự kiện đẩy từ khóa lên component cha.
  • AddUser: Quản lý form nhập liệu thêm mới người dùng (với các trường đơn và trường lồng nhau address). Khi người dùng nhấn nút thêm, component đóng gói dữ liệu và gọi hàm callback gửi lên App.
  • ResultTable: Chịu trách nhiệm nạp dữ liệu người dùng ban đầu từ Mock API (jsonplaceholder.typicode.com/users) qua useEffect, thực hiện lọc danh sách dựa trên keyword nhận từ App, lắng nghe người dùng mới qua prop user, đồng thời trực tiếp xử lý các nghiệp vụ Sửa (Edit Modal) và Xóa (Delete).
2

Sơ đồ Luồng dữ liệu & Nâng trạng thái (State Lifting)

Câu hỏi: Tại sao state "kw" và "newUser" lại được đặt ở component App mà không đặt ở SearchForm hay AddUser?

Đây là bài toán kinh điển giải quyết bằng kỹ thuật Lifting State Up (Nâng trạng thái lên cha) trong React vì các lý do cốt lõi sau:

1. Luồng dữ liệu một chiều (One-way Data Flow) và quan hệ giữa các Component ngang hàng (Sibling Components):
Trong kiến trúc React, dữ liệu chỉ truyền từ trên xuống dưới (từ Cha xuống Con) thông qua Props. Hai component con cùng cấp không thể trực tiếp nói chuyện hoặc can thiệp vào state của nhau. SearchForm, AddUser và ResultTable là ba component ngang hàng (anh/em ruột) cùng nằm trong App.

2. Phân tích đối với state "kw" (Từ khóa tìm kiếm):
• Nơi phát sinh sự kiện thay đổi dữ liệu: Người dùng gõ phím tại thẻ <input> nằm trong SearchForm.
• Nơi tiêu thụ dữ liệu để lọc: Danh sách người dùng users và biểu thức users.filter(...) lại nằm trọn vẹn trong ResultTable.
➔ Nếu ta để state kw nằm cục bộ bên trong SearchForm, dữ liệu từ khóa sẽ bị "giam hãm" (encapsulated) tại đó. ResultTable sẽ hoàn toàn không thể biết được người dùng đang gõ gì để tiến hành lọc dữ liệu. Do đó, state kw bắt buộc phải được "nâng" lên component cha chung gần nhất là App. App truyền hàm setter setKeyword xuống cho SearchForm kích hoạt, đồng thời truyền giá trị kw xuống ResultTable để lọc bảng.

3. Phân tích đối với state "newUser" (Người dùng mới tạo):
• Nơi thu thập dữ liệu: Form nhập liệu modal/inline thuộc về component AddUser.
• Nơi quản lý và hiển thị danh sách: Mảng dữ liệu người dùng users thuộc về ResultTable.
➔ Tương tự như trên, khi người dùng bấm "Thêm", AddUser không thể tự mình nhảy sang ResultTable để chèn vào mảng users. Giải pháp chuẩn là AddUser đẩy đối tượng mới lên App thông qua callback onAdd(user). Sau đó App lưu vào newUser và chuyển tiếp xuống ResultTable qua prop user={newUser}. Tại ResultTable, hook useEffect([user]) sẽ phát hiện thay đổi và đưa người dùng mới vào mảng, rồi báo ngược lại cho App thông qua callback onAdded() để giải phóng state (đưa về null).

4. Tuân thủ nguyên lý Single Source of Truth (Nguồn chân lý duy nhất):
Đặt state tập trung tại App giúp ứng dụng dễ kiểm soát luồng dữ liệu, tránh tình trạng bất đồng bộ dữ liệu giữa các thành phần giao diện, code minh bạch, dễ bảo trì và mở rộng sau này.

3

Mô tả Props được truyền từ App xuống các Component con

Dưới đây là bảng đặc tả đầy đủ các Props được truyền từ component cha App xuống ba component con, thể hiện chính xác nguyên lý State Lifting và One-way Data Binding:

Component nhận Tên Prop Kiểu dữ liệu Chiều truyền Ý nghĩa và Chức năng hoạt động
SearchForm onChangeValue Function (callback) Cha ➔ Con (callback kích hoạt ngược lên Cha) Nhận hàm setKeyword từ App. Mỗi khi người dùng gõ phím vào ô tìm kiếm, sự kiện onChange sẽ kích hoạt hàm này kèm giá trị chuỗi nhập vào e.target.value, giúp cập nhật tức thời state kw tại App.
AddUser onAdd Function (callback) Cha ➔ Con (callback kích hoạt ngược lên Cha) Nhận hàm setNewUser từ App. Khi người dùng hoàn tất điền form và nhấn "Thêm người dùng", hàm này được gọi và truyền đối tượng user vừa tạo lên lưu vào state newUser của App.
ResultTable keyword String Cha ➔ Con (truyền giá trị dữ liệu) Nhận giá trị chuỗi từ khóa kw hiện tại từ App. ResultTable dùng prop này trong hàm users.filter() để so khớp (không phân biệt hoa thường) với name và username, từ đó quyết định những dòng nào được hiển thị trên bảng.
ResultTable user Object | null Cha ➔ Con (truyền đối tượng dữ liệu) Nhận đối tượng người dùng mới được lưu ở state newUser của App. ResultTable dùng hook useEffect([user]) để lắng nghe khi prop này khác null, lập tức thêm đối tượng đó vào mảng danh sách users nội bộ.
ResultTable onAdded Function (callback) Cha ➔ Con (callback kích hoạt ngược lên Cha) Nhận hàm callback () => setNewUser(null) từ App. Sau khi ResultTable đã thêm thành công người dùng mới vào mảng users, hàm này được kích hoạt để đưa state newUser ở App về lại null, ngăn chặn việc re-render lặp lại không mong muốn.

Lỗi (Warning / Error) gặp phải trong quá trình code và Giải pháp

Trong quá trình hiện thực mã nguồn theo tài liệu hướng dẫn thực hành, ứng dụng đã ghi nhận và xử lý triệt để 4 lỗi cùng cảnh báo kỹ thuật quan trọng sau:

Lỗi Error nghiêm trọng
Lỗi 1: Vòng lặp re-render vô hạn ("Too many re-renders")

1. Hiện tượng & Thông báo lỗi:

Uncaught Error: Too many re-renders. React limits the number of renders to prevent an infinite loop.

Khi người dùng mở form thêm người dùng (AddUser), trang web lập tức bị treo hoặc crash trắng màn hình với thông báo lỗi đỏ rực trong DevTools Console.

2. Nguyên nhân sâu xa:

Trong tài liệu hướng dẫn mẫu tại trang 6 có đoạn code cho nút bấm "Hủy":
<button onClick={setAdding(false)}>Hủy</button>.
Khi viết onClick={setAdding(false)} (có cặp dấu ngoặc đơn gọi hàm ngay), JavaScript sẽ thực thi hàm setAdding(false) ngay trong giai đoạn render của component chứ không phải chờ người dùng bấm chuột (click). Khi setAdding(false) được gọi, nó làm thay đổi state, buộc React phải re-render component. Trong lần re-render tiếp theo, hàm lại tiếp tục bị gọi ngay lập tức, tạo thành một vòng lặp vô hạn (Infinite Render Loop). React phát hiện số lần render vượt quá giới hạn an toàn nên đã ngắt luồng và ném ra ngoại lệ trên.

3. Cách khắc phục:

Chuyển lời gọi hàm thành một hàm ẩn danh (Arrow Function callback) để React chỉ thực thi hàm khi sự kiện click thực sự diễn ra:

SAI: Gọi hàm ngay khi render Lỗi vô hạn 
{/* Gọi hàm trực tiếp -> Infinite loop */}
<button onClick={setAdding(false)}>
  Hủy
</button>
ĐÚNG: Bọc trong Arrow Function Đã khắc phục 
{/* Chỉ gọi hàm khi người dùng click */}
<button onClick={() => setAdding(false)}>
  Hủy
</button>
Lỗi Error Runtime
Lỗi 2: Sập giao diện khi đọc thuộc tính lồng nhau ("Cannot read properties of undefined")

1. Hiện tượng & Thông báo lỗi:

TypeError: Cannot read properties of undefined (reading 'street') at ResultTable

Khi người dùng thêm một đối tượng người dùng mới mà bỏ trống thông tin địa chỉ hoặc khi người dùng được nạp từ nguồn dữ liệu không có trường address, toàn bộ bảng bị sập hoàn toàn.

2. Nguyên nhân sâu xa:

Tại đoạn render trong bảng: <td>{u.address.street}, {u.address.suite}, {u.address.city}</td>, code giả định luôn luôn tồn tại đối tượng u.address. Khi u.address là undefined hoặc null, việc truy cập vào u.address.street sẽ làm JavaScript ném lỗi TypeError.

3. Cách khắc phục:

Sử dụng kiểm tra an toàn hoặc toán tử Optional Chaining (?.) trước khi truy cập và hiển thị chuỗi:

SAI: Truy cập trực tiếp không kiểm tra Dễ vỡ (Fragile) 
<td>
  {u.address.street}, 
  {u.address.suite}, 
  {u.address.city}
</td>
ĐÚNG: Kiểm tra an toàn trước khi hiển thị An toàn & Bền vững 
<td>
  {u.address ? [u.address.street, u.address.suite, u.address.city].filter(Boolean).join(", ") : "—"}
</td>
Cảnh báo Console Warning
Lỗi 3: Xung đột ID trùng lặp Key khi Thêm người dùng sau khi Xóa ("Duplicate Key")

1. Hiện tượng & Cảnh báo Console:

Warning: Encountered two children with the same key, '10'. Keys should be unique so that components maintain their identity across updates.

Ban đầu danh sách có 10 người dùng với ID từ 1 đến 10. Khi người dùng bấm xóa người dùng ở giữa danh sách (ví dụ người dùng #5), mảng còn lại 9 phần tử. Nếu tiếp tục bấm thêm một người dùng mới, phần tử mới lại được gán ID bằng prev.length + 1 = 9 + 1 = 10. Lúc này trong bảng xuất hiện 2 phần tử có cùng key=10, khiến React đưa ra cảnh báo trùng key và làm sai lệch thuật toán Virtual DOM Reconciliation.

2. Nguyên nhân sâu xa:

Công thức prev.length + 1 chỉ đúng khi danh sách chỉ tăng mà không bao giờ bị xóa. Khi có thao tác xóa phần tử, độ dài mảng giảm xuống nên không còn tương ứng với giá trị ID lớn nhất hiện tại.

3. Cách khắc phục:

Sử dụng Math.max() duyệt qua toàn bộ các ID hiện có để tìm ID lớn nhất rồi cộng thêm 1, đảm bảo ID luôn tăng dần và duy nhất tuyệt đối:

SAI: Dựa vào độ dài mảng prev.length Dễ trùng Key 
// Khi xóa bớt rồi thêm mới -> Trùng ID đã có!
setUsers((prev) => [
  ...prev, 
  { ...user, id: prev.length + 1 }
]);
ĐÚNG: Tìm Max ID hiện có trong danh sách Duy nhất 100% 
// ID luôn lớn hơn ID cao nhất trong mảng
setUsers((prev) => {
  const nextId = prev.length > 0 
    ? Math.max(...prev.map(u => Number(u.id) || 0)) + 1 
    : 1;
  return [...prev, { ...user, id: nextId }];
});
Lỗi Logic Giao diện & Tham chiếu
Lỗi 4: Đột biến State qua tham chiếu do Shallow Copy đối tượng lồng nhau khi Sửa (Deep Copy)

1. Hiện tượng sai lệch logic:

Bug Logic: Khi người dùng bấm nút "Sửa" và gõ thay đổi địa chỉ trên form modal, dữ liệu dòng tương ứng trên bảng ngoài tự động nhảy chữ theo thời gian thực dù người dùng CHƯA bấm "Lưu". Nếu bấm "Hủy", dữ liệu gốc trong bảng vẫn bị thay đổi và không thể khôi phục!

2. Nguyên nhân sâu xa:

Trong JavaScript, toán tử spread { ...user } chỉ thực hiện sao chép nông (Shallow Copy) ở tầng ngoài cùng. Đối tượng con user.address vẫn dùng chung con trỏ tham chiếu vùng nhớ với đối tượng trong state users của bảng. Khi form sửa thực hiện thay đổi trường con editing.address.street = value, nó đã vô tình trực tiếp sửa đổi (Mutate) state gốc, vi phạm nguyên tắc Immutability của React.

3. Cách khắc phục:

Thực hiện sao chép sâu (Deep Copy) cả đối tượng con address khi mở form sửa:

SAI: Shallow copy giữ nguyên tham chiếu address Đột biến State 
function editUser(user) {
  // LỖI: address vẫn trỏ chung vùng nhớ trong users!
  setEditing({ ...user });
}
ĐÚNG: Deep Copy cả đối tượng con address Độc lập an toàn 
function editUser(user) {
  // ĐÚNG: Tách rời hoàn toàn bản sao của address
  setEditing({
    ...user,
    address: { ...(user.address || { street: "", suite: "", city: "" }) }
  });
}
